# 붕괴 위험 카드 쿨타임 곱셈 전환 계획 (2026-11-06)

> 상태: 0·1·2단계를 C 판에 적용했다(JS 판 미적용). 결과와 계획 대비 바뀐 점은 [전수조사 보고서의 적용 결과](gimmick-perf-census.md#적용-결과-같은-날-재측정)에 있다.

근거: [gimmick-perf-census.md](gimmick-perf-census.md)(26,662조합 실측). 목표는 연쇄·대상 곱 기믹이 웹에서 60Hz를 유지하고 대상·이벤트·개체 상한에 닿지 않게 하는 것이다. 기본 덱(`적 → 마탄` 같은 단일 슬롯)의 쿨타임은 가능한 한 그대로 둔다.

## 1. 현재 규칙의 문제

- 쿨타임 = 0.016에서 시작해 카드 연산(`+ − × =`)을 **배치 순서대로** 적용한다([slots.c calculate_cooldown](../c/sim/slots.c), [js cooldown.js](../js/cards/cooldown.js)).
- `×`를 앞에 두면 0.016에 곱해져 거의 공짜가 된다. 그래서 보상 카드는 지금 `+`만 쓴다(cooldown.js 주석).
- 곱 기믹의 실행 비용은 **호스트 수 × 뒤 대상 수 × 생성 개체 수 ÷ 쿨타임**이다. 그런데 `+` 가산은 카드 몇 장이 겹쳐도 몇 초를 더할 뿐이라 곱을 따라가지 못한다.

## 2. 대상 카드 선정

L2 20,352조합으로 `log(틱 ms) = 생성기 + 연쇄 + 대상 + 행동` 회귀를 해서 카드마다 **한계 비용 배수**를 구했다. 배수는 같은 종류에서 가장 싼 카드 대비 값이다. 시간초과는 하한값으로 넣었으므로 실제 배수는 이보다 크다. 선정 기준은 대상·연쇄 카드는 배수 1.5 이상, 행동 카드는 2.0 이상이다(행동은 뒤 대상의 영향이 섞여 전반적으로 높게 나온다).

## 3. 규칙 변경 (1단계: 카드 곱셈)

### 3.1 데이터

- `data/cards.csv`에 `cdMul` 열(기본 1)과 `cdMulScope` 열(`always`|`chain`, 기본 `chain`)을 추가한다. 기존 `cd` 연산(`+0.9` 등)은 그대로 둔다. 가산은 유지하고 곱만 더하는 방식이다.
- `data/card_ui.csv`의 `cdop` 표기는 `+0.9 ×2.75`처럼 둘을 함께 보여 준다.
- 손볼 곳:
  - [c/tools/gen_data.py](../c/tools/gen_data.py): 열 검증(1 이상의 수, scope 값)과 `Card.cd_mul`·`cd_mul_chain` 생성.
  - [tools/export-csv.cjs](../tools/export-csv.cjs) / [js cooldown.js](../js/cards/cooldown.js): JS 쪽 표가 card_ui를 다시 내보내므로 같은 값을 넣거나, 기준을 C로 정하고 [C_JS_PARITY.md](../docs/C_JS_PARITY.md)에 차이로 기록한다.

### 3.2 계산 (곱은 가산 합 뒤에 한 번)

```
sum = 0.016, mul = 1
카드를 배치 순서대로:
  '=' → sum = 값, mul = 1        (개체 주기 덮어쓰기 유지: 변형의 '='는 곱도 지운다)
  '+'/'−' → sum ±= 값
  '×'(기존 연산) → mul *= 값
  cdMul 적용 조건이면 → mul *= cdMul
쿨타임 = max(0.016, sum × mul)
```

- 곱이 위치와 무관해진다. 앞에 놓으면 공짜가 되는 문제가 사라지고 기존 `×` 연산도 같은 규칙을 따른다(현재 데이터에는 `×` 카드가 없어 결과는 같다).
- **연쇄 구간**: 슬롯에서 첫 행동 뒤 첫 연쇄 카드부터 끝까지가 연쇄 구간이다. 생성된 연쇄 슬롯은 전부 연쇄 구간이다. `chain` 범위의 곱은 여기서만 적용한다. 그래서 `적 → 마탄`·`전체 → 폭발` 같은 단일 슬롯은 쿨타임이 바뀌지 않고, 연쇄 뒤에 놓을 때만 무거워진다.
- **항상**: 생성 행동(분열·소환·포탑·미끼·구체·지뢰)과 조건형 연쇄 카드는 단일 슬롯에서도 곱한다. L1에서 연쇄 없이 붕괴한 11조합이 모두 「넓은 대상 → 생성 행동」이었기 때문이다. 예: `적 → 기사 소환` 1.37초 → 3.07초.
- 원본 슬롯의 쿨타임은 지금처럼 연쇄 뒤 카드까지 전체로 계산하므로 같은 곱을 받는다.
- 수정 위치: [slots.c calculate_cooldown](../c/sim/slots.c)(구조 분석 캐시에 들어가 매 틱 비용은 없다), 같은 규칙의 JS `slotCooldown`.

|---|---:|---:|

## 4. 1단계만으로 되는 범위 (실측 기반 예측)

비용이 쿨타임에 반비례한다고 보고 L2 결과(장면 기본 0.45ms 제외)에 위 곱을 적용해 봤다.

| L2 등급 | 지금 | 예측 |
|---|---:|---:|
| 안전 | 11,588 | 13,996 |
| 주의 | 3,844 | 2,843 |
| 위험 | 1,643 | 1,437 |
| 붕괴(시간초과 아님) | 1,591 | 390 |
| 붕괴(시간초과) | 1,686 | 1,686 (해결 불가로 가정) |

**시간초과 1,686조합은 카드 곱으로 못 막는다.** 이 조합들은 호스트 200~1600 × 대상 200~3000이라 필요한 배수가 수백~수만이다. 카드 쿨타임은 카드 조합만 알고 실제 개수는 모른다. 그래서 2단계가 필요하다.

## 5. 2단계: 실행 결과 곱 (개수에 비례하는 쿨타임)

같은 「쿨타임 곱셈」을 카드 대신 실제 개수로 건다. 연쇄 슬롯은 한 번 실행한 뒤 다음을 곱한다.

1. **생성 수 곱**: 행동이 만든 개체 수 c가 `K_SPAWN`(초기 8)을 넘으면 `cd × c / K_SPAWN`. 플레이어 슬롯에도 적용한다. 이것으로 L1 자기 증식(`전체 → 기사 소환`)이 스스로 멈춘다.
2. **대상 수 곱**: 연쇄 슬롯이 고른 대상 수 n이 `K_TARGET`(초기 16)을 넘으면 `cd × n / K_TARGET`.
3. **호스트 공유 곱**: 같은 카드 스택·같은 행동 주체의 연쇄 슬롯 수 H가 `K_HOST`(초기 32)를 넘으면 `cd × H / K_HOST`. add_link가 이미 같은 스택을 찾으므로, 스택별 개수를 `fast.` 파생 색인(저장 제외)으로 센다.

세 곱을 다 걸면 연쇄 슬롯 하나의 초당 실행량이 `K_HOST × K_TARGET × K_SPAWN ÷ 기본 쿨타임`으로 묶인다. 장면 크기와 무관하게 상한이 생긴다. 상수는 `data/constants.csv`에 두고 전수조사로 맞춘다. 화면 표시는 연쇄 슬롯 조회 화면의 `남은 시간 / 쿨타임`에 실제 적용된 값을 보여 준다.

## 6. 0단계: 동작 불변 성능 수정 (먼저 해도 되는 것)

조건형 연쇄 슬롯이 `can_act`(빙결·공포) 검사보다 먼저 대상 선택과 조건 평가를 한다. 얼어 있는 호스트 200이 아무것도 쏘지 않으면서 단독 네이티브로 7~12ms/틱을 쓴다. 검사 순서만 앞으로 옮기면 된다(결과 동일, 쿨타임 소모 규칙 동일). 저장·규칙 시험 동등성으로 확인한다.

## 8. 정할 것

- **JS 판 동기화**: 데이터 원본은 같은 CSV지만 JS `cooldown.js`가 쿨타임 표를 따로 가진다. C만 바꾸고 차이를 기록할지, JS도 같이 바꿀지 정해야 한다(AGENTS 기준이면 C 우선).
- **2단계 체감**: 개수 곱은 넓은 대상 연쇄 기믹을 「느리지만 큰 한 방」으로 바꾼다. 상수가 작으면 화면이 붐빌 때 연쇄가 거의 안 도는 것처럼 보일 수 있으므로, 상수를 정한 뒤 실제 플레이로 확인한다.
