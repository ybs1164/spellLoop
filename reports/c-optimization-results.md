# C 최적화 검증 결과

동일한 충돌 결과를 유지한 선택안은 적 3,000마리 장면에서 렌더링을 포함한 실제 게임 루프가 JS보다 **2.01배·2.22배** 빨랐다. 이 선택안을 일반 C 웹 빌드에 반영했으며, 최종 바이너리의 성능 재측정은 진행 중이다. 아래 후보 측정값을 최종 배포 빌드의 확정 수치로 해석하면 안 된다.

## 측정 범위

- Windows, i5-1135G7, Iris Xe / ANGLE D3D11, Chrome 156.0.8078.80, 1280×720, DPR 1.
- JS는 기존 WASM 수학·공간 처리와 WebGL을 활성화한 상태다. JS·데이터·참조 WASM 113개 파일의 해시가 최초 비교 시점과 같다.
- 배속은 `JS 평균 CPU 프레임 시간 / C 평균 CPU 프레임 시간`이다. 시뮬레이션, C 위치 보간, 그리기와 화면 제출을 포함한 원래 게임 루프를 측정했다. 60Hz 화면의 FPS가 두 배라는 뜻은 아니다.
- 초기 개체·입력·카드 구성을 맞췄으며 C의 기존 충돌 처리 순서와 매 틱 계산을 유지했다. 두 구현에 원래 존재하는 동작 차이는 [초기 분석](c-js-performance-analysis.md)의 범위를 따른다.

## 선택안의 반복 측정

| 순서 | 측정 프레임 | JS 실제 루프 | C 실제 루프 | JS/C |
|---|---:|---:|---:|---:|
| JS → C | 180 | 12.194ms | 6.061ms | 2.01배 |
| C → JS | 240 | 14.647ms | 6.611ms | 2.22배 |

원자료: [첫 측정](generated/c-js-performance/outline93-c-js.json), [역순 측정](generated/c-js-performance/outline93-c-js-repeat.json). 선택한 행은 두 파일의 `C-c`다. `C-e`는 루프 펼치기를 제한한 별도 실험으로, 일관된 이득이 없어 반영하지 않았다. 이 표의 C는 일반 경로를 분리한 후보 빌드이며, 정식 빌드 재측정 결과를 별도로 확인해야 한다.

## 반영한 변경

- 공간 인덱스를 연속 배열과 논리 셀로 구성하고 SIMD로 명백히 충돌하지 않는 후보를 건너뛴다. 실제 충돌의 스칼라 순서·조회 상한·부동소수점 연산 순서는 유지한다.
- 충돌 직전과 직후에 만들었다가 다시 버리는 공개 인덱스 구성을 틱 내부에서 생략한다. 적 재배치 뒤 다음 공개 조회 전에 다시 구성한다.
- 후보 전체가 조회 상한 안에 들어오는 경우 이전 ID의 개수 계산을 생략하고, 일반 조회·예외 경로를 별도 함수로 유지한다.
- 반복되는 반지름 조합, 카드 메타데이터와 일반 슬롯의 해석 결과를 캐시한다. 개체의 실제 스탯과 카드 스택으로 행동을 결정하는 규칙은 그대로다.
- 개체 배열 사이에 캐시 패딩을 추가하고 기존 저장 형식의 크기 표기를 유지한다. 파생 캐시는 저장하지 않는다.
- 공유 아틀라스, 스프라이트 UV 캐시, 그림자·본체 인스턴스 결합, GPU 업로드 버퍼 재사용과 UI 캐시를 사용한다. 대표 장면은 두 번의 인스턴스 드로로 그린다.
- 실제 실행 횟수를 이용하는 PGO를 일반 웹 빌드에 연결했다. 프로파일은 빌드 때만 사용하며 배포 파일에 계측 코드를 넣지 않는다. `fast-math`, 근사 역수, 업데이트 생략은 적용하지 않았다.

## 동작·렌더링 검증

| 검증 | 결과 |
|---|---|
| 네이티브 규칙 시험 | 136/136, 카드 구현 101/101 |
| WASM 규칙 시험 | 136/136, 카드 구현 101/101 |
| 원본 C와 전체 상태 비교 | 네이티브 12/12, WASM 12/12 비트 일치 |
| 원본 저장 파일 불러오기 | 두 플랫폼 각각 12/12 일치, v3/v4 호환 시험 통과 |
| 픽셀 비교 | 27개 화면, 채널 차이 최대 2/255, 그보다 큰 차이 없음 |
| 웹 플레이 확인 | 하위 경로 정적 호스팅, 시작·이동·일시정지·도감·개체 조회·편집기·리사이즈 통과 |

상태 비교는 시드 1·7·31에서 일반 3,600틱, 복합 카드 1,800틱, 투사체·설치물 90틱, 적 3,000마리 90틱을 각각 실행한다. 독립 충돌 참조 시험에는 조회 상한, 여러 반지름, 큰 좌표, 셀 경계 이동, 늦게 생성된 개체와 인덱스 예외를 포함한다. 픽셀 비교에는 DPR 1·2·1.25, 상태 효과와 좌우 반전을 포함한다.

원자료: [네이티브 상태 비교](generated/c-js-performance/optimization-differential.json), [WASM 상태 비교](generated/c-js-performance/optimization-differential-wasm.json), [픽셀 비교](generated/c-js-performance/release-final-render-equivalence.json).

## 최종 성능 측정의 제한

정식 빌드 재측정 중 외부 CPU 부하가 커져 C가 프레임당 평균 3.5–5.3틱을 따라잡는 실행이 발생했다. 이 값은 위의 약 1틱/프레임 측정과 작업량이 달라 목표 달성 판단에 사용하지 않았다. 불리한 결과도 [전체 장면 부분 기록](generated/c-js-performance/release-system-load-partial.json), [최종 빌드 재시도](generated/c-js-performance/release-final-crowd.json)에 남겼다. 벤치마크에는 시작 전·장면별 호스트 CPU 사용률 기록을 추가했다. 다른 앱 종료나 OS 전원·우선순위 변경은 하지 않았다.

일부 함수는 코드 구조가 바뀌어 이전 PGO 계수가 무시되고 일반 최적화로 컴파일된다. 컴파일러 경고를 숨겨 계수를 강제로 적용하지 않는다. 캐시와 아틀라스를 위한 추가 메모리를 사용하며, 현재 수치는 이 CPU·GPU·브라우저 조건에 한정된다.

## 재현

```powershell
python c/tools/build.py web --site c/build/site/c
python c/tools/bench_web.py --test
$env:NODE_PATH=(npm root -g)
$env:PERF_REAL='1'
$env:PERF_FRAMES='120'
$env:PERF_OUTPUT='reproduction.json'
node tools/bench-c-js.cjs
```

실행 기록 재수집은 `python c/tools/train_web_pgo.py`, PGO 대조 빌드는 `python c/tools/build.py web --no-pgo`로 수행한다. Chrome·Playwright·emsdk가 필요하며, 프로파일 재수집의 최초 실행에는 해당 LLVM 버전의 런타임을 다운로드한다. SDK가 프로파일을 읽지 못하면 일반 최적화 빌드로 폴백한다.
