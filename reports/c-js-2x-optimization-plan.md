# 최적화 JS 대비 C 웹 2배 성능 계획

작성: 2026-11-03. 목표는 **현재 JS의 WASM·WebGL 최적화를 켠 상태보다 C 웹의 CPU 프레임 시간을 절반 이하로 줄이는 것**이다. FPS와 CPU 처리 비용을 구분하고, 개체의 스탯·슬롯·카드 스택으로 행동을 결정하는 규칙을 유지한다.

## 1. 현재 위치와 목표

이번 계획은 현재 소스와 기존 측정 자료를 분석한 결과이며, 새 빌드·성능 실험은 실행하지 않았다. 작업 트리에 기존 변경이 많으므로 아래 기록을 현재 소스의 확정 성능으로 간주하지 않는다.

가장 최근 집중 측정인 [release-final-focused.json](generated/c-js-performance/release-final-focused.json), 180프레임 기준:

| 장면 | DPR | JS 실제 루프 평균 | C 실제 루프 평균 | JS/C | 2배에 필요한 C 상한 |
|---|---:|---:|---:|---:|---:|
| 적 3,000 | 1 | 14.754ms | 7.972ms | 1.85배 | 7.377ms |
| 적 1,000 + 탄 2,000 | 1 | 9.313ms | 4.714ms | 1.98배 | 4.657ms |
| 적 3,000 | 2 | 14.959ms | 8.036ms | 1.86배 | 7.479ms |
| 적 1,000 + 탄 2,000 | 2 | 11.096ms | 4.665ms | 2.38배 | 5.548ms |

- 수치상 DPR 1 밀집 장면은 C 시간을 약 **7.5%**, 탄막은 **1.2%** 더 줄이면 2배 경계에 도달한다. 흔들림을 고려해 구현 목표는 **현재 C 대비 15~20% 단축**으로 잡는다.
- 이전 후보의 2.01~2.22배 기록은 [기존 결과](c-optimization-results.md)에 있다. 최신 집중 측정은 그 문서의 미확정 상태 이후 자료이므로 함께 봐야 한다.
- 최신 기록의 C는 평균 1틱/프레임이지만 장면별 호스트 CPU 사용률은 약 23~77%로 달랐다. 비율은 재확인이 필요하다.
- 동적 탄막은 종료 시 C 탄 1,009개, JS 탄 2,005개로 갈라진다. 효과·피해 글자 수도 다르므로 이 비율은 각 제품의 실행 비용 비교이며, 같은 충돌 작업량의 처리 속도 증명으로 쓰지 않는다.

## 2. 이미 끝난 최적화와 남은 병목

현재 C에는 유인·구조물 인덱스, 공통 아틀라스, 인스턴싱, 업로드 버퍼 재사용, 슬롯 구조 캐시, 충돌 SIMD, LTO·PGO가 있다. 최초 분석의 전체 탐색 제거·6,053 draw call 축소를 새 작업으로 반복하지 않는다.

- 최신 밀집/탄막 정적 렌더는 C 각각 **2 draw**, 업로드 **205,696 / 717,696바이트**다. 추가 draw call 감소보다 CPU 준비·순회·전송량을 먼저 본다.
- [최근 프로파일](generated/c-js-performance/release92-profile-c-crowd3000-real.cpuprofile)의 전체 샘플 중 `sim_step` self 39.1%, `run_kind` 11.9%, `draw` 7.6%, `grid_build` 4.2%다. `sim_step`에는 인라인된 코드가 포함되므로 밀어내기 비용으로 단정하지 않는다.
- [이전 분리 프로파일](generated/c-js-performance/profile48-c-crowd3000-real.cpuprofile)에서는 후보 조회·밀어내기가 컸다. 현재도 우선 확인할 가설이며, 옛 비중을 예상 가속률로 사용하지 않는다.
- [entities.c](../c/sim/entities.c)의 `run_kind`는 종류마다 `0..hi`를 다시 훑고, [render.c](../c/render/render.c)의 월드 렌더도 종류별 순회를 반복한다.
- [slots.c](../c/sim/slots.c)는 구조 분석을 캐시하지만 매 조회 카드 해시·비교, `Analysis` 복사, 이동 전후 단계 판별과 이벤트 수신 여부 탐색은 남아 있다.

## 3. 실행 순서

| 순서 | 작업 | 적용 위치 | 통과 기준 |
|---|---|---|---|
| P0 | 비교 기준·단계 계측 정리 | `tools/bench-c-js.cjs`, `c/tools/bench_web.py`, `c/tools/bench_web.inc` | 반복 측정과 같은 작업량 비교가 가능함 |
| P1 | 실제 병목에 맞춰 밀어내기 후보 처리 개선 | `c/sim/spatial.c` | 밀집 장면 전체 루프 8~12% 단축을 실험 목표로 설정 |
| P2 | 종류별 활성 인덱스로 반복 순회 축소 | `c/sim/world.c`, `entities.c`, `world.h`, `c/render/render.c` | 밀집·탄막·개체 대량 소멸 후 회귀 없이 추가 단축 |
| P3 | 슬롯 실행 계획·이벤트 메타데이터 확장 | `c/sim/slots.c`, `deck.c`, `world.c` | 복합 카드·보석·소환 장면 개선, 전체 상태 일치 |
| P4 | 렌더 데이터 생성 축소·PGO 재학습 | `c/render/render.c`, `gfx.c`, `gfx_web.h`, `c/profiles/` | 최종 배포 경로에서 반복 목표 통과 |

각 항목은 독립 변경으로 측정한다. 개선율은 측정 전 보장하지 않으며 단순 합산하지 않는다. P1의 비중이 작으면 P2·P3를 먼저 수행하고, 목표를 만족하면 남은 고위험 변경을 진행하지 않는다.

### P0: 비교 신뢰도부터 확보

1. C·JS·CSV·참조 WASM·PGO·최종 바이너리 해시, 빌드 옵션, 브라우저·GPU·해상도를 측정 결과에 기록한다. JS 기준을 고정한다.
2. 계측 빌드와 정식 빌드의 결과를 구분한다. 정식 `c/build/site/c`의 원래 루프로 최종 확인할 수 있는 외부 계측 경로를 마련한다.
3. 계측기의 `--phases`는 여전히 `separate_enemies(w)` 문자열을 감싸지만 실제 틱은 `separate_enemies_for_tick(w)`를 호출한다. 이 누락을 수정하고 각 훅의 삽입·호출 횟수를 검증한다. 계측 오버헤드가 있는 빌드는 병목 분해용으로만 사용한다.
4. 두 비교를 함께 수집한다: **제품 실제 루프**와 **작업량을 고정한 시뮬레이션·렌더**. 후자는 초기 상태·틱 수·활성 수를 고정하고, 충돌은 같은 좌표·반지름·후보 및 조회 상한을 쓰는 별도 커널 장면을 추가한다. C와 JS의 기존 규칙 차이는 기록한다.
5. C·JS 양쪽에서 실제 틱/진행 시간, 활성 적·탄·효과·글자, 슬롯 실행·후보 검사·실제 충돌 수를 기록한다. C의 누적 틱이나 JS의 갱신·충돌 예산 차이로 생긴 작업량 차이를 식별한다.
6. 예열 후 300프레임 이상, 실행 순서를 교대해 5쌍 이상 측정한다. 호스트 부하·발열 변동이 큰 실행은 원자료에 남기고 사전 정의한 기준으로 재측정한다. 실행 중 전체 CPU 사용률은 게임 자체의 부하도 포함한다.

### P1: 밀어내기 후보 처리

- `separation_query`, `separate_packed`, 셀 구성·갱신을 분리 계측하고 후보 수, 실제 겹침 수, SIMD 탈락률, 일반 경로 진입률을 센다.
- 기존 연속 후보 구간·셀별 컷·반지름 캐시를 유지하며, 중복 셀 메타데이터 조회와 빈 후보 처리를 줄인다. 우선 일반 경로를 분리해 작은 빈번 경로의 코드 크기를 줄이는 방식을 대조한다.
- SIMD는 이미 존재한다. 추가 SIMD 폭 확대보다 실제 탈락률과 스칼라 대체 경로 비용을 먼저 확인한다.
- **후보 순서·512개 조회 상한·순차 좌표 갱신·부동소수점 계산 순서를 보존한다.** 밀어낸 좌표가 다음 쌍의 결과에 영향을 주므로 모든 충돌 쌍의 일괄 병렬화나 틱을 넘긴 후보 재사용은 기본안에서 제외한다.
- 큰 좌표·해시 충돌·셀 경계 이동·다양한 반지름·죽거나 새로 생긴 개체를 포함해 기존 스칼라 참조와 비교한다.

### P2: 종류별 활성 인덱스

- 기존 `decoys`·`structures` 비트셋 방식을 종류별 활성 인덱스로 확장하고, 틱·렌더에서 해당 종류의 ID만 순회한다. 일괄 압축 목록과 비트셋을 실제 장면에서 대조한다.
- ID 오름차순과 `run_kind` 시작 시점의 `hi` 상한을 보존한다. 같은 단계에서 생긴 개체가 기존 빈 ID를 재사용하는 경우도 기존 실행 여부를 유지한다.
- 생성·해제·종류 변경·저장 불러오기에서 인덱스를 갱신한다. 파생 인덱스는 저장하지 않는다.
- 공개 격자는 현재도 여러 단계에서 필요하다. 이동·소환·밀어내기·재배치로 질의 결과가 바뀌므로 재구축을 일괄 한 번으로 합치지 않는다. 결과 불변이 입증된 구간만 재사용한다.
- 별도 스트레스 장면은 대량 생성→대량 소멸 후 높은 `hi`, 화면 밖 10,000개, 설치물·아군 다수로 구성한다.

### P3: 슬롯 실행 계획 확장

- 현재 2,048칸 구조 캐시에 슬롯별 버전/계획 핸들을 연결해 변경 없는 카드 스택의 해시·전체 비교와 큰 분석 구조 복사를 줄인다. 공유 계획의 수명·교체를 명시한다.
- 첫 행동, 이동 전후 단계, 이벤트 수신 비트, 정적 카드 메타데이터를 계획에 둔다. 종류별 전용 AI를 추가하지 않고 실제 슬롯 스택에서 계획을 만든다.
- 카드 추가·삭제·정렬, 변형 값 변경, 연쇄 슬롯 생성·만료, 저장 불러오기에서 무효화한다. `afterMovement`처럼 변형 값이 관여하는 필드는 카드 ID만으로 캐시하지 않는다.
- 동적 스탯·버프·대상·쿨타임은 기존 시점에 계산한다. 잠든 동안 누적 시간을 한 번에 빼는 방식은 부동소수점·이벤트 시점이 달라질 수 있으므로 별도 의미 검증 없이 도입하지 않는다.

### P4: 렌더·PGO 마무리

- P2의 활성 목록을 월드 렌더에도 활용하고, 반복 색상·스프라이트·그림자 메타데이터와 글자 폭 조회를 프로파일에 따라 줄인다. DPR·폰트·덱 변경 시 기존 UI 캐시 무효화를 확인한다.
- 탄막 업로드는 C 717,696바이트, JS 월드 481,296바이트다. HUD 등 측정 범위가 다르므로 전량을 낭비로 보지 않고, CPU 인스턴스 생성과 GPU 제출을 나눠 측정한 뒤 패킹 축소를 검토한다.
- 현재 두 번인 draw를 한 번으로 줄이는 작업은 절감 시간이 확인될 때만 진행한다. 반투명 그리기 순서를 유지한다.
- 최종 소스에 맞춰 PGO를 재수집하고 `--no-pgo` 대조를 수행한다. 기존 프로파일 불일치 경고와 일반 최적화 폴백을 확인한다. 학습하지 않은 장면도 검증한다.

## 4. 완료 기준과 검증

- 주 목표: 적 3,000 및 적 1,000+탄 2,000, DPR 1·2에서 반복 쌍별 `JS 평균 CPU / C 평균 CPU`의 중앙값 **2.0 이상**. 반복 분산과 신뢰구간도 공개하고 경계에 걸리면 실행 수를 늘린다.
- 안정성: 핵심 장면 C CPU p95가 16.67ms 이하이며, 일반 장면·효과·도감·편집기에서 측정 오차를 넘는 회귀가 없어야 한다. rAF 간격·진행 틱·버린 누적 시간도 함께 공개한다.
- 작업량 고정 실험에서는 ms/틱, ms/동일 렌더, 후보 수·실제 충돌 수를 별도로 보고한다. 제품 루프의 2배와 같은 연산의 2배를 혼동하지 않는다.
- 규칙·상태: `python c/tools/build.py test`, WASM 규칙 시험, 네이티브/WASM `check_optimization_replay.py`로 기준 C와 상태·저장 호환을 비교한다. 수정한 경계 조건과 슬롯 무효화만 추가 검증한다.
- 렌더·플레이: 기존 DPR 1·2·1.25 픽셀 비교, C 정적 배포의 시작·이동·일시정지·편집·도감·저장/불러오기 확인을 재수행한다.
- 최종 검증은 `python c/tools/build.py web --site c/build/site/c` 결과를 정적 서버로 열어 수행한다. 메모리 피크·WASM 크기도 전후로 기록한다.

## 5. 현재 C에서 추가 2배를 뜻하는 경우

이 목표는 JS 대비 2배보다 크다. 최신 DPR 1 C 기록 기준 밀집 **3.986ms**, 탄막 **2.357ms** 이하가 필요하다. P0에서 비중을 다시 확정한 뒤 P1~P4의 합산 결과로 판단한다.

예를 들어 전체 시간의 60%인 부분만 개선한다면 그 부분을 6배 빠르게 해야 전체가 2배가 된다. 작은 캐시·컴파일 옵션만으로 약속할 수 없으며, 목표에 못 미치면 슬롯 실행 계획의 범위를 넓히고 공간 자료 구조·렌더 준비를 함께 재설계해야 한다. 멀티스레드·갱신 생략·충돌 예산 변경은 실행 순서나 게임 동작에 영향을 줄 수 있어 이 계획의 기본 단계에 포함하지 않는다.
