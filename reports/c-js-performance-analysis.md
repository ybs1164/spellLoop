# C·JS 웹 성능 비교 및 C 최적화 분석

측정일: 2026-11-02. 현재 작업 트리의 C 웹 Release와 JS 기본 웹 버전을 비교했다. **현재 전투 부하에서는 JS 기본 버전이 유리하며, C의 가장 큰 개선 여지는 언어 수준이 아니라 전체 개체 탐색과 렌더 배칭에 있다.** 게임 동작 변경 없이 별도 계측 진입점·벤치마크·결과 파일을 추가했다.

## 측정 조건과 해석

- Windows, Intel Core i5-1135G7(4코어/8스레드), Iris Xe, Chrome 156.0.8078.74 headless. 양쪽 모두 실제 Intel D3D11 ANGLE을 사용했으며 SwiftShader를 강제하지 않았다.
- 1280×720 CSS px, DPR 1/2. C는 SDL3 GLES2/WebGL 1, JS는 WebGL 2 인스턴싱 + Canvas2D + DOM HUD다. **JS 기본 버전은 이미 C/WASM 연산 코어를 사용한다.** 워커는 사용하지 않았다.
- C는 `python c/tools/build.py web --site c/build/site/c`로 최신 Release(-O3)를 빌드했다. 별도 계측 빌드는 동일한 시뮬레이션·렌더·SDL 오브젝트를 링크하고 함수 이름을 보존했다. 원래 SDL 진입점의 고정 틱/보간/실시간 루프도 별도로 호출해 검증했다.
- 두 버전에 같은 스테이지·적 종류·좌표 생성식·초기 개체 수·플레이어 카드 스택을 넣었다. 자동 스폰을 억제하고 생존 체력을 높였다. 각 개체의 실제 스탯·슬롯·카드 실행 경로는 유지한다. 이펙트는 시각 전용 데이터다.
- 정적 렌더: 같은 초기 장면을 20프레임 예열 후 120프레임 측정. 로직: 30틱 예열 후 120틱. 1틱은 1/60초. 핵심 네 장면은 새 브라우저에서 45프레임 재측정했다.
- 로직 열은 C `sim_step`, JS `game.update`다. **JS의 DOM HUD 갱신은 로직 열에, C HUD 그리기는 렌더 열에 포함**된다. 두 열을 독립 측정했으므로 합계로 실제 프레임 시간을 만들면 안 된다.
- 렌더 열은 그리기 명령 생성·WASM↔JS 경계·SDL 명령 처리·제출 시간이다. rAF에 맞춰 측정해 브라우저가 정상적으로 합성하도록 했다. `gl.finish`를 포함한 별도 결과도 JSON에 저장했다. 이는 순수 GPU 시간이나 DOM 최종 페인트 시간이 아니다. 실제 루프의 rAF 간격으로 최종 처리량을 보완했다.
- UI 수치는 화면을 연 후의 반복 프레임 비용이다. JS의 DOM 생성·최초 레이아웃 비용은 제외되며, 정적인 DOM이 매 프레임 재생성되지 않는 구조적 이점이 반영된다.
- 합성 스트레스 시험으로, 일반 플레이의 보장 FPS나 C 언어 자체의 속도 비교는 아니다. 전투 중 양쪽 충돌/갱신 정책이 달라 상태가 갈라진다. 특히 탄막 로직은 동일한 계산량·결과를 보장하는 마이크로벤치가 아니다. `initial`, `afterSim`, `afterLive`에 실제 수를 저장했다.
- 화면 밖 10,000마리 장면은 **렌더 스캔/컬링만** 측정했다. 로직을 돌리면 게임의 재배치가 적을 화면 근처로 옮기므로 해당 장면의 로직·실시간 수치는 분석에서 제외한다.

## 실제 기본 프레임 루프 재측정

## GPU 명령과 업로드

DPR 1, 예열 후 정적 한 프레임. WebGL API 호출을 별도 프레임에서 감싸 세었으므로 타이밍 수치에는 이 계측 비용이 들어가지 않는다. **JS draw call은 월드 WebGL 배치만 세며, 바닥·피해 글자의 Canvas2D와 DOM HUD의 브라우저 내부 draw call은 포함하지 않는다.** C는 HUD까지 같은 WebGL 경로다. 이 범위 차이를 감안해도 6,053 대 1의 주된 원인은 적마다 끊기는 C 월드 배치다.

| 초기 장면 | C GL draw | JS 월드 GL draw | C 버퍼 업로드 KiB | JS 월드 업로드 KiB |
| --- | --- | --- | --- | --- |
| 빈 전투 | 53 | 1 | 36.66 | 0.33 |
| 적 400 + 보석 300 | 853 | 1 | 388.12 | 61.27 |
| 적 3,000 | 6053 | 1 | 1724.16 | 140.95 |
| 적 1,000 + 탄 2,000 | 2053 | 1 | 2005.31 | 470.02 |
| 적 150 + 원 100 + 파티클 600 + 글자 100 | 355 | 1 | 6842.91 | 40.17 |

`gfx_rect`는 무텍스처, `gfx_sprite`는 스프라이트 텍스처를 사용한다. 적 하나의 그림자→몸체 뒤에 다음 적의 그림자가 오면서 단색/텍스처 상태가 바뀌고 배치가 끊긴다. SDL GLES2도 동일 텍스처·블렌드·스케일 상태의 인접 명령만 합친다. JS는 몸체·그림자 합성 비트맵, 흰 픽셀 단색 사각형, 여러 스프라이트를 한 아틀라스에 담아 순서를 유지하면서 한 번에 인스턴싱한다.

C 효과 장면의 버퍼 업로드는 약 6.68 MiB/프레임이다. 원형 디더·도트 도형을 다수 사각형/삼각형으로 풀어 SDL이 정점을 재구성한다. JS는 반복 모양의 원을 `PixelCircle` 도장으로 캐시해 이 장면의 월드 업로드가 약 40 KiB다. 단순 텍스처 정렬로 순서를 바꾸면 알파 합성이 달라지므로, 순서를 유지하는 아틀라스/도장 방식이 적합하다.

## CPU 프로파일로 확인한 C 병목

프로파일은 1ms 샘플링, 장면·단계별 약 2.5초이며 일반 타이밍과 분리했다. 백분율은 샘플 시간 비중으로, 함수 안에 인라인된 코드도 해당 함수 이름에 들어간다.

1. **3,000 적 로직: `r_self` 약 60.4%.** [targets.c](../c/sim/targets.c)의 `r_self`→`redirected_player`가 유인 대상을 찾으려고 `w->hi` 전체를 훑는다. 유인 개체가 없어도 적마다 같은 검사를 반복한다. 적 N마리에 대해 대략 N×전체 개체 수가 된다. 같은 프로파일에서 `grid_query` 약 8.4%, `data_str` 약 5.4%다.
2. **탄막 로직: `tick_shot` 약 64.1%.** [entities.c](../c/sim/entities.c)의 투사체 처리는 적 격자 조회 뒤, 구조물·아군 충돌을 위해 다시 모든 `w->hi`를 순회한다. 시험에는 구조물·아군이 없는데도 이 경로를 탄마다 돈다. 적/탄 수가 함께 늘수록 급격히 불리하다. `r_self`도 약 8.3%다.
3. **3,000 적 렌더: GL 상태 설정/경계 호출.** 프로파일 전체의 `vertexAttribPointer` 약 15.9%, `drawArrays` 약 3.7%, `useProgram` 약 3.3%다. rAF 대기 `(idle)` 약 60.1%를 뺀 활성 시간에서는 각각 약 40%, 9%, 8%다. 이는 GPU 실행 시간 비중이 아니라 CPU 샘플이다.
4. **탄막 렌더: 정점 재구성과 상태 설정.** `GLES2_QueueGeometry` 약 9.9%, `vertexAttribPointer` 약 10.3%, `wasm-to-js` 약 6.2%로, 픽셀 외에 SDL 정점 변환과 API 경계 비용도 크다.
5. **JS의 남은 로직 부하는 겹침 해소다.** 3,000 적 프로파일의 `wasm-function[27]`은 내장 WASM export 확인 결과 `separate`이며 약 70.5%를 차지했다. 탄막에서도 약 40.8%다. JS는 이미 전체 개체 탐색·스프라이트 제출을 줄여 공간적 밀집 처리 쪽으로 병목이 옮겨져 있다.

## JS 기본 버전과 WASM을 끈 경로

JS 기본 버전의 이점에는 기존 WASM 공간 격자·이동·충돌/휴면 경로가 포함된다. 이를 구분하려고 같은 벤치마크에서 `WasmCore.enabled=false`도 측정했다. WebGL 렌더는 유지한다. 이 설정은 WASM 연산 경로를 끄며, 시작 시 로드한 WASM 메모리/SoA 저장 공간까지 제거하는 별도 제품 빌드는 아니다.

| 초기 장면 | C 웹 로직 | JS 기본(WASM 켬) | JS 연산 폴백(WASM 끔) |
| --- | --- | --- | --- |
| 빈 전투 | 0.02 | 0.13 | 0.09 |
| 적 400 + 보석 300 | 1.70 | 0.46 | 2.46 |
| 적 3,000 | 32.73 | 3.09 | 14.26 |
| 적 1,000 + 탄 2,000 | 40.06 | 2.71 | 10.94 |

JS는 먼 적·과밀 적/탄의 갱신 주기, 충돌 예산, 겹침 해소 예산, 가려진 개체 그리기 제한도 사용한다. C는 대부분 매 틱 전체를 처리한다. 기본 버전의 차이는 이런 작업량 정책까지 포함한다. 모든 정책을 동일하게 고정하지 않고 언어만의 배수로 해석하면 안 된다.

## C 최적화 우선순위

C에도 SoA 개체 풀·슬롯 free list·공간 격자·화면 밖 컬링·바닥 텍스처·글리프 아틀라스·인접 텍스처 배치가 이미 있다. 이 기반을 유지하고 남은 전체 탐색과 배치 단절을 줄이는 것이 적합하다.

| 순서 | 변경 후보 | 근거/주의사항 |
| --- | --- | --- |
| 1 | 유인 기능을 가진 활성 개체 목록/공간 인덱스를 유지하고, 목록이 비면 즉시 플레이어 반환 | 3,000 적 로직 샘플 약 60%가 집중됨; 유인 범위·팀·동률 순서와 슬롯에 의한 생성/해제의 즉시 반영을 보존해야 함 |
| 2 | 투사체의 구조물·아군 충돌을 종류별 목록/별도 격자로 제한 | 빈 구조물 목록에도 전체 탐색하는 O(탄×전체 개체) 제거; 충돌 순서·관통·최근 타격 기억·이벤트 연쇄를 보존해야 함 |
| 3 | 월드 단색·스프라이트·실루엣의 공통 아틀라스와 흰 픽셀, 그림자/몸체 합성 캐시 | 적 3,000에서 6,053 GL draw; 그리기 순서를 바꾸지 않고 텍스처 전환을 줄이는 것이 핵심; 필요하면 그다음 전용 인스턴싱 경로 검토 |
| 4 | 원·그림자·디더 등 반복 도형을 도장/메시로 캐시 | 효과 장면 약 6.68 MiB/프레임 업로드; 픽셀 격자·디더 홀짝·DPR·투명도·애니메이션 진행도를 캐시 키에 반영; 임의 양자화는 시각 변경과 구분 |
| 5 | 슬롯의 구조 분석과 카드/표 참조를 미리 컴파일 | `run_slot`이 실행 전에 `analyze`와 쿨타임/속성 조회를 반복; actions/triggers/조건 목록·문자열 키를 정수/함수 포인터로 캐시하되 동적 스탯·버프·변형에 따른 값은 갱신 |
| 6 | 활성 종류별 개체 인덱스, 이벤트 리스너 인덱스, 격자 dirty 갱신 | `run_kind`와 렌더의 여러 hi 순회, 매 틱 네 번 격자 재구축, 피크 이후 빈 칸 스캔 감소; 이동·밀어내기·재배치 뒤의 질의 의미가 달라 네 번을 무조건 한 번으로 합치면 안 됨 |
| 7 | 도감/편집기 레이아웃·줄바꿈·문자폭·카드 그룹 캐시, 정적 UI 레이어 재사용 | 도감 반복 비용 8~13ms; viewport/DPR/font/덱 버전/필터 변경 때 무효화; 타이틀 바닥이나 애니메이션은 계속 갱신 |
| 8 | nearest 1개는 선형 최소 탐색, 소수 k개는 제한된 top-k | 현재 `nearest_enemies`는 1개를 요청해도 후보를 전부 qsort; 대상 순서·동률·반경/제외 규칙을 보존해야 함 |
| 9 | 메모리의 hot/cold 분리와 글꼴/에셋 로딩 축소 | 아래 메모리/로딩 항목 참고; 첫 세 병목보다 프레임 개선 우선순위는 낮음 |

우선 1·2·3을 서로 분리해 적용하고 같은 장면으로 재측정하는 것을 권한다. 슬롯·카드 모델은 유지하면서 조회/실행/그리기의 자료 구조를 바꾸는 작업이다. 예상 가속 배수는 구현·검증 전에는 확정할 수 없으며, 위 프로파일 비중을 그대로 가속률로 제시하지 않았다. LTO/SIMD/전역 fast-math/스레드화는 이 구조적 낭비를 해결한 뒤 검토하는 편이 효율적이다.

## 메모리·로딩·보간

- C `sizeof(World)`는 **57,166,568바이트(약 54.52 MiB)**다. 65,536개 개체, 131,072개 슬롯과 상태/스택/효과 저장 공간을 처음부터 확보한다. 기존 SoA는 유지할 가치가 있지만, 자주 쓰는 필드와 드문 상태·이벤트 자료의 분리는 검토할 수 있다.
- C WASM linear memory는 일반 장면에서 약 76.8 MiB, 효과 부하 후 약 110.6 MiB로 늘었다. 메모리 증가는 반환된 뒤에도 브라우저에 같은 크기의 linear memory가 남을 수 있다. 도형 정점/SDL 임시 버퍼 피크도 줄일 대상이다.
- JS 기본의 `native/sim_core.wasm` 초기 linear memory는 별도 인스턴스 확인 기준 약 **66.88 MiB**다. JSON의 기존 `heapBytes`는 C에서는 WASM, JS에서는 JS heap이므로 직접 비교하면 안 된다. 재측정 결과에는 `wasmBytes`와 `jsHeapBytes`를 분리했다. GPU 텍스처·브라우저 래스터·프로세스 전체 RSS는 이 값에 포함되지 않는다.
- C 정적 배포 파일은 약 **6.70 MiB**, 그중 `.data` 약 **5.16 MiB**다. TTF 두 개가 5,395,104바이트로 패키지 대부분이다. JS 원본 woff2 합계는 671,368바이트다. 안전한 글자 서브셋·압축 전송·필요 자원 로딩 분리의 여지가 있다. 이번 로컬 서버의 loadMs는 네트워크 다운로드 벤치마크가 아니므로 인터넷 로딩 속도 배수로 해석하지 않는다.
- 보간은 x/y/gen 스냅샷과 x/y 임시 이동·복원을 수행한다. 별도 `interpolation` 결과를 저장했으며 현재 큰 비용은 아니다. 렌더 시 좌표를 직접 보간하는 방식은 후순위다.

## 범위와 검증 한계

대표 적·투사체·보석·원형 효과·파티클·피해 글자·바닥·HUD·타이틀·일시정지·편집기·도감을 실측했다. 스폰/타깃/슬롯/상태/충돌/사망/저장 및 플랫폼 루프는 코드도 확인했다. 개별 보스/모든 장판·소환 조합, 워커 모드, 모바일 실기기, C 네이티브 데스크톱 렌더와 소비 전력은 별도 실측하지 않았다. 순수 GPU 타이머나 브라우저 합성 스레드 CPU를 별도 분해한 결과는 없다.

같은 개발 PC에서 반복 측정했으며 OS/GPU 전용 격리 환경은 아니다. 핵심 장면 재측정에서도 결론은 유지됐으나 C의 3,000마리 정적 렌더 평균은 약 38~52ms로 흔들렸다. p95와 원자료를 함께 보고 작은 수치 차이보다 병목 구조를 우선 판단해야 한다. 양쪽 픽셀 동일성이나 긴 플레이의 규칙 동등성을 이 벤치마크로 보증하지 않는다.
