# 인게임 최적화 계획

목표: 적 400 · 보석 300 · 탄 100 동시 상황에서 `Game.step` 4ms 이하, 렌더 포함 60fps 유지. 게임 규칙(스탯·슬롯·카드 스택)과 결과는 바꾸지 않는다.

## 진행 결과

측정: `node tools/bench-frame.cjs` (600프레임, `step(1/60)`), 단계별 `node tools/bench-frame.cjs stageN` (다양한 덱, 무적, 보스 처치 또는 300초).

| 시나리오 | 전 | 후 |
| --- | --- | --- |
| 적 134 (덱 없음) | 16.35ms | 1.37ms |
| 적 117 + 기본 덱 | 16.32ms | 1.56ms |
| 보석 301 | 19.49ms | 1.41ms |
| 혼합 적 351 + 탄 45 | 118.78ms | 6.62ms |
| stage3 / stage5 / stage6 | 17.4 / 37.6 / 71.3ms | 2.0 / 4.3 / 5.6ms |
| stage7 (심연의 옥좌) | 측정 생략 (20분 이상) | 9.4ms (p95 19.6ms) |
| `play-stages` 3시드 400초 | 114초 | 17초 |

- **1~3단계는 결과가 같다**: 모든 시나리오의 상태 지문(`fp`), 고정 시드 `play-stages` 결과, 렌더 픽셀 해시(DPR 1·1.5·2)가 변경 전과 동일하다.
- **1단계**: 유인 후보 캐시, 개체별 카드 환경 캐시, 대상 래퍼 재사용, 최근접 적 선형 탐색.
- **2단계**: 효과 서명 비교를 스탯 파생값 비교로, 슬롯 실행 환경 재사용(재진입 시 복사), 카드 정의 캐시, **대상 지연 해석**(쿨타임 중인 행동은 대상을 해석하지 않음 — 난수·상태를 바꾸는 `randomPoint`·`prey`는 즉시 해석), 근처 적 수 세기·공간 해시 셀 재사용, 화상 피해 합 증분 계산.
- **3단계**: 아군·파티클·글자·이펙트 화면 밖 컬링(흔들림 포함 여유), F3 성능 오버레이, `tools/bench-render.cjs`. 렌더 JS 비용은 적 380 장면에서 약 3ms이고 나머지는 래스터 비용이다. 스프라이트 `save/restore` 제거는 DPR 1.5에서 픽셀이 달라지거나(직접 좌표) 이득이 없어(변환 복원) 적용하지 않았다. HUD 갱신은 0.005ms라 손대지 않았다.
- **4단계**: 측정 중 `전염`이 한 프레임 안에서 이웃 적끼리 스택을 서로 복사해 스택 수가 기하급수로 늘어나 한 프레임이 최대 37초 멈추는 문제를 찾았다. 남은 시간이 같은 화상·표식 스택을 합치고(화상은 초당 피해 합, 표식은 중첩 수 `count`) 피해량·표식 배율 규칙은 유지했다. 이후 전염 덱에서도 100ms를 넘는 프레임이 없다.
- **슬롯 실행 계획 컴파일**: 카드 목록이 바뀔 때만 카드 스택을 읽어 대상 묶음·행동별 주기·충돌·소환 설정, 대상 조건, 사망 연계, 미룸 여부를 계획으로 만든다. 실행할 때는 계획을 순회하며 대상 해석과 쿨타임 판정만 하고, 행동 실행은 `executeStep` 하나로 처리한다(미뤄진 실행은 원래처럼 카드 스택을 다 읽은 뒤의 주기 설정을 본다). 결과는 이전과 동일하다.
- **남은 비용**(stage7 구간별): 적 슬롯 갱신 약 4ms, 적 탄 슬롯 약 2ms, 적 밀어내기 약 2ms. 밀어내기 질의 반경을 실제 최대 반경으로 줄이면 0.5ms 빨라지지만, 밀어내는 도중 움직인 적을 다르게 찾아 결과가 달라져 적용하지 않았다.
- **보류**: 보석은 이미 350개 초과 시 병합되고 300개에 1.7ms라 추가 병합은 하지 않았다. 화면 밖 적 갱신 주기 축소도 적 400에서 예산 안이라 적용하지 않았다(쿨타임·이동이 미세하게 달라지는 규칙 변경).

찾은 원인과 조치 (결과는 모두 이전과 동일 — 상태 지문·플레이스루·체크포인트 비교):

- **개체 생성**: 적 하나에 40~380µs. 카드 변형을 찾으려고 효과를 복사·`JSON.stringify` 하고, 이미 정렬된 카드 목록을 다시 정렬하고, 개체마다 스탯 접근자 함수 40개를 만들었다. 입력 문자열 캐시, 정렬 생략, 스탯 접근자를 프로토타입 클래스(`EntityCombatStats`)로 옮겨 대부분 15~50µs가 됐다. 스탯 이름 목록은 `ENTITY_STAT_NAMES`로 공개한다.
- **새 개체의 첫 갱신**: 카드 환경마다 행동 위임 함수 45개를 새로 만들던 것을 공유 함수(`this.owner` 사용)로 바꿨다.
- **적 밀어내기**: 밀집 시 한 프레임 3.6~4.9만 쌍을 검사하며 쌍당 약 250ns가 들었다(적 객체 형태가 38가지로 갈려 속성 읽기가 느림). 같은 칸·같은 순서로 타입 배열 위에서 계산해 0.6ms 안팎이 됐다. 적 생성자에서 나중에 붙는 상태 필드를 미리 선언해 형태도 하나로 맞췄다.
- **장판 대량 발동**: 잔불 정령이 한꺼번에 죽어 화염 장판 76개가 같은 프레임에 발동하면, 장판마다 전체 개체(약 600개)를 감싸 조건을 걸었다(11.5ms). `전체` 대상에 거리 조건이 붙으면 같은 거리 판정으로 먼저 거르고, 부작용 없는 조건들은 한 번에 거른다(약 7ms).
- **대량 대상 행동**: `전체 적 → 화상/공포`는 대상 380~400개마다 범위 판정을 해 상태 적용이 1.9만~4.7만 번 일어난다. 대상마다 같던 피해 계산을 한 번으로 줄이고 범위 질의 배열을 재사용해 17~21ms → 10~17ms가 됐다. 나머지는 규칙상 필요한 양이다.
- **남은 스파이크는 렌더**: 브라우저에서 업데이트 p99는 stage6 8.5ms, stage7 13ms인데, 렌더 p99는 19~41ms다. 렌더 스파이크는 대량 대상 행동이 원형 이펙트 상한(250개)과 파티클 상한(600개)을 채우는 프레임과 겹치고, 그 프레임에서 JS 그리기는 약 2ms이고 나머지는 래스터다(헤드리스 소프트웨어 래스터라 실제 GPU보다 크게 나온다). 이펙트 수를 줄이는 것은 화면이 바뀌는 변경이라 적용하지 않았다.
- 실행마다 위치가 바뀌는 30~80ms 이상값은 재현되지 않아 GC·환경 잡음으로 판단했다(GC 정지는 최대 4.5ms).

## 렌더링 2차: 같은 그림은 한 번 구워 한 번에 찍기

목표: 스트레스 테스트(stage7, 240초, 적 최대 400·원형 이펙트 250) 렌더 최대 10ms. 측정: `NODE_PATH=$(npm root -g) STRESS_RECHECK=8 node tools/stress-browser.cjs [저장소]` — 같은 실행 환경에서 변경 전 → 후를 연달아 측정.

| 렌더 (헤드리스 Chromium, 소프트웨어 래스터) | 전 | 후 |
| --- | --- | --- |
| 평균 | 16.0ms | 5.6ms |
| p99 | 59.7ms | 15.9ms |
| 10ms 초과 프레임 | 8050 / 14400 | 1469 |
| 재측정 p99 / 최대 (VM 순간 정지 제외) | 53.1 / 87.8ms | 11.5 / 15.4ms |
| 재측정 10ms 초과 | 7537 | 408 |

- 이 VM 은 같은 코드도 실행마다 속도가 최대 2배 달라지고 수십~백여 ms 순간 정지가 있어(업데이트도 같은 정지를 보임) 원래 최대값은 지표로 쓸 수 없다. `STRESS_RECHECK` 는 느린 프레임을 같은 상태로 두 번 더 그려 최솟값을 따로 기록한다.
- 이 환경에서 확대 `drawImage` 는 같은 크기 복사의 약 5배, 같은 크기 복사도 `fillRect` 의 약 4~8배 비용이고, 디더 패턴 칠은 단색보다 10배 느리다. 그래서 **호출 수와 패턴 칠을 줄이는 것**이 핵심이다. WebGL 묶음 그리기는 이 환경(SwiftShader)에서 배경 한 장에 9ms 가 들어 제외했다.

적용한 기법 (게임 상태·난수 소비는 그대로 — `bench-frame` 지문 동일, 모든 `check-*` 통과):

1. **스프라이트 타일 캐시** (`Sprites.tile`): 확대·좌우 반전·색조를 화면 배율 해상도로 미리 구워 `save/translate/scale/restore` 없이 1:1 로 찍는다.
2. **몸체 합성 = 같은 스프라이트 묶음** (`Sprites.bodyFamily/drawBody`): 적의 그림자·불꽃 아우라(밝기 0.02 단계)·본체·종족 색조를 한 캔버스로 합성한다. 같은 종류·방향·흔들림 단계의 적은 모두 같은 캔버스를 쓰고, 변형은 정수 번호로 찾아 문자열을 만들지 않는다. 적 하나가 3~5회 호출 → 1회. 그림자·아우라는 3px 격자 대신 스프라이트에 맞춰져 최대 1px 움직인다.
3. **도장 캐시** (`Px.band/ellipse/ring`): 디더 원·큰 단색 원·장판 테두리를 모양(행별 스팬)·칠·패턴 위상 키로 구워 한 번에 찍는다. 매 프레임 바뀌는 색은 두 번째로 쓰일 때만 굽고, 직전 도장을 기억해 같은 원이 연달아 오면 계산을 건너뛴다. 일렁이는 광채는 `rgba` 문자열 대신 불투명 색 + `globalAlpha` 로 바꿔 같은 도장을 재사용한다(같은 결과).
4. **원형 이펙트 합성** (`PixelCircle`): 대량 대상 행동이 같은 프레임에 만드는 같은 반지름·진행도의 원을 면·띠·반짝이까지 투명도(1/32 단계)째 구워 원 하나를 한 번에 찍는다. 반짝이 배치 seed 를 8가지로 줄였다(난수 호출 수는 같음).
5. **바닥 한 번 칠하기**: 지우기 색·어두운 톤·단계 색조를 바닥 패턴에 구워 전체 화면 칠 3번 → 1번.
6. **피해 숫자 비트맵**: 그림자 포함 글자를 구워 `fillText` 2번 → `drawImage` 1번 (글꼴 로드 후).
7. **적 컬링 여백**을 실제 그리는 범위(스프라이트·방패·머리 위 표시)로 줄였다 (화면 결과 동일 확인).

화면 비교(`DPR 1`, 고정 시드 3장면): 1~3·5 는 최대 3/255 반올림 차이, 2·4·6 은 그림자 1px 이동·반짝이 위치·페이드 중 글자 그림자만 다르다 (육안 동일).

**남은 비용 (목표 미달)**: 10ms 를 넘는 프레임은 적 약 390 + 원형 이펙트 약 240 이 겹칠 때다. 적 4~5ms(개체당 호출 1~2회가 하한), 이펙트 2ms, 바닥 1ms, 글자 0.8ms. 더 줄이려면 화면이 바뀌는 선택이 필요하다: 이펙트 상한(250) 축소나 과부하 시 반짝이 생략, 상태 색조(빙결·화상 깜빡임)를 몸체에 합성(메모리 증가). 실제 GPU 브라우저에서는 래스터가 GPU 로 가므로 호출 수 감소의 효과가 더 크다. 업데이트도 같은 장면에서 p99 18ms 라 프레임 전체 10ms 는 업데이트 최적화가 별도로 필요하다.

## 단계별 작업

### 1단계 — O(N²) 제거 (예상 효과 가장 큼)

1. **미끼 목록 프레임 캐시** (`game.js` `redirectedPlayerTarget`)
   - `step()` 시작 시 `entityDecoy`가 켜진 개체만 모은 `this.decoys`를 한 번 만들고, `redirectedPlayerTarget`은 이 목록만 순회한다.
   - 미끼가 없으면 즉시 `{ kind: 'self' }` 반환.
   - `chaseTarget`·`playerTarget`이 같은 개체에 대해 프레임당 여러 번 부르므로 `unit._chaseFrame/_chaseTarget` 메모를 둔다.
2. **`allTargets()` 프레임 캐시**
   - `this.frame` 카운터로 무효화하고, 개체 추가·제거(`push`/`compact`) 시 dirty 처리.
   - 대상 래퍼 `{ kind, e }`는 개체에 한 번만 만들어 재사용(`o._target`). 카드가 래퍼를 수정하지 않는지 확인 후 적용.
3. **`nearestEnemies` 교체**
   - 현재: 전체 적 순회 + 정렬 + `slice` + `map`.
   - 변경: 범위가 유한하면 공간 해시 질의, `n === 1`이면 정렬 없이 최솟값만, 그 외는 부분 선택.
   - `enemyNear`(n=∞)·`clusterPoint`(후보 40개마다 `hash.query(..., [])`)·유도탄 재탐색이 직접 혜택을 받는다.

### 2단계 — 슬롯 실행 비용 절감

4. **개체별 카드 환경 캐시** (`cardEnv`, `EntitySlot.update`)
   - `CARD_EFFECTS` 위임 함수와 질의 함수는 `owner`만 다르므로 프로토타입(클래스) 메서드로 옮기고, 환경은 개체당 한 번 생성해 `owner.slot._env`에 보관한다.
   - `EntitySlot.update`의 `{ ...baseEnv, ... }` 전개를 없애고 `deathEvent` 등 가변 필드만 갱신한다.
5. **슬롯 컴파일**
   - `changed()` 시점에 카드 스택을 `[{ filters, targetCards, actions: [{ card, interval, teamRule, summonMode, deferred }] }]` 형태의 실행 계획으로 미리 만든다.
   - 매 프레임 `forEach` + `prevType` 분기 + `execute` 클로저 생성을 계획 순회로 대체한다. 슬롯 → 조건 → 대상 → 행동 순서는 그대로 유지.
   - `has(id)`가 `enabled`가 있을 때도 `cards.some(cardBaseId…)`를 도는 경로를 컴파일된 `Set`으로 대체.
6. **효과 해석 캐시** (`configuredEffect`)
   - `JSON.stringify` 서명 대신 `combatStats` 세터에서 올리는 `owner.statsVersion` + 카드 id로 캐시 키를 만든다.
   - 스탯·카드가 바뀌지 않으면 `entityResolvedEffect`의 객체 복사 자체를 건너뛴다.
7. **작은 핫패스 정리**
   - `Projectile.cardTick`: `slot.has('entityMove')` 2회 → 1회.
   - `collideShot`·`collideStructures`: `[...this.objects, ...this.allies]` 전개를 두 배열 직접 순회로.
   - `crowd`·`enemiesAround`·`clusterPoint`의 `hash.query(..., [])`를 재사용 버퍼로.
   - `SpatialHash.clear()`가 셀 배열을 매 프레임 버리므로 셀을 유지하고 길이만 0으로(프레임 스탬프 방식).

### 3단계 — 렌더링

8. **컬링 누락 보완**: 아군(`allies`)·장판(`drawZones`)·적 탄(`drawHazards`)·이펙트(`drawFx`)도 `inView`로 거른다.
9. **도트 도형 캐시**: `Px.band`/`disc`/`ellipse`는 행마다 `fillRect`를 호출하므로 큰 장판·그림자는 `(반지름, 색, 격자)` 키로 오프스크린 캔버스에 미리 그려 `drawImage` 한 번으로 그린다. `drawShadow`가 우선 대상.
10. **파티클·텍스트 배치**: 색·투명도 단계별로 묶어 `fillStyle`/`globalAlpha` 변경 횟수를 줄인다. 피해 숫자는 동일 문자열 비트맵 캐시 검토.
11. **HUD**: `updateBuffHud`가 매 프레임 키 문자열을 만들므로 버프 변경·정수 초 변경 시에만 계산.

### 4단계 — 개체 수 상한 정책 (규칙 영향 있음, 별도 승인 후)

12. 화면 밖 먼 보석이 일정 수(예: 200)를 넘으면 가까운 보석끼리 합친다. 기존 `분열`과 같은 방식으로 경험치 합은 유지하되, 슬롯을 가진 개체를 합치는 규칙이므로 도입 여부를 먼저 결정한다.
13. 화면 밖 적의 슬롯 갱신 주기 축소(예: 2프레임에 1번 + dt 누적)는 쿨타임·이동 결과가 미세하게 달라지므로 측정 후 필요할 때만.

## 10000 개체 계획: 시뮬레이션 워커 분리 (실험, `?worker=1`)

- **구성**: `js/sim-worker.js`(워커: `Game`을 헤드리스로 돌리고 보이는 것만 스냅샷 전송) + `js/sim-bridge.js`(메인: 스냅샷으로 복제 개체를 만들어 기존 `Game.render`·개체 `draw`를 그대로 사용). `SharedArrayBuffer` 대신 전송 가능한 `Float32Array`(적 행 20필드)와 평범한 객체 사본을 쓰므로 COOP/COEP 헤더가 필요 없다. `http(s)` 에서 `?worker=1` 로 열 때만 켜지고, 그 외(`file://` 포함)는 기존 메인 스레드 시뮬레이션 그대로다.

- **측정** (`WORKER_ENEMIES=N NODE_PATH=$(npm root -g) node tools/check-worker-sim.cjs`, 헤드리스 소프트웨어 래스터, VM 편차 큼):

| 적 수 | 메인 프레임 평균 (업데이트+렌더) | 워커 틱 (시뮬+스냅샷) | 스냅샷/초 |
| --- | --- | --- | --- |
| 약 700 | 9.7ms | 8.1ms | 39.5 |
| 약 12000 | 18~23ms (p95 25~35) | 32~41ms | 14.5~22 |

  기존(메인 스레드)은 같은 규모에서 업데이트 약 23ms + 렌더 약 15ms = 약 38ms였다. 메인 프레임은 렌더만 남아 절반 가까이 줄었지만 16.6ms는 헤드리스 래스터 기준으로 아직 못 미치고, 시뮬레이션은 워커에서 초당 15~22틱으로 돈다.

## 10000 개체 4차: 카드 이벤트 예산과 투사체·장판 경로 (`tenk`)

측정 환경: 다른 학습 작업이 CPU 를 거의 다 쓰는 VM 이라 벽시계가 실행마다 2배까지 흔들린다. 그래서 변경 전 사본과 **번갈아** 쟀다.

| tenk (같은 시간대 번갈아 3회) | 변경 전 | 변경 후 |
| --- | --- | --- |
| step 평균 | 57 ~ 89ms | 20 ~ 26ms (부하가 덜할 때 17 ~ 19ms) |
| p95 | 227 ~ 373ms | 35 ~ 46ms |
| step / 기준 작업(`BENCH_CAL`) | 58 | 15.5 ~ 17 |
| 단계 (ms) | 충돌 21~34, 장판 13~20, 투사체 11~17, 적 10~14 | 투사체 8~10, 적 6~8, 장판 5~6, 충돌 2~3 |

**16ms 목표는 이 환경에서 아직 확인하지 못했다** (부하가 가장 낮았던 실행 16.9ms). 같은 코드를 CPU 를 나눠 쓰지 않는 기계에서 다시 재야 한다.

결과가 같은 변경 (예산을 끈 상태에서 `play-stages`·`check-snap-pack`·모든 bench 지문이 변경 전과 동일):
- **투사체 충돌 WASM** (`shot_next`): 칸 정렬 격자를 C 가 훑어 겹친 적만 하나씩 돌려준다. 후보마다 그 차례의 좌표로 판정하는 것도 같다.
- **가까운 적 WASM** (`near_scan`): `nearestEnemies` 의 거리 판정을 C 가 하고, n 이 작으면 정렬 대신 상위 n 개만 끼워 넣는다 (같은 거리면 목록 앞선 적). 연쇄 번개가 적 5000 을 매번 정렬하던 비용이 사라졌다.
- **`entityArea`(범위 내 적)**: C `cull` 로 먼저 거른다 (장판 288 개 × 적 5000 선형 순회).
- **유인 후보**: 어떤 개체 슬롯에도 유인 카드가 없으면(`entityDecoySlots`) 목록을 훑지 않는다.
- **`ownerListens`**: 카드 배열별 발동 종류 비트 캐시.
- **휴면**: 쿨타임 없는 표는 1프레임 뒤 잠들고 15~30 프레임 엇갈려 잔다 (동시에 생긴 개체가 한꺼번에 깨어나 튀던 프레임 완화).
- **효과 해석 공유**: 같은 효과·같은 참조 스탯 값이면 개체끼리 결과 객체를 공유.
- 할당 줄이기: `resolveProjectileEnds`·`resolveEntityDeaths` 의 배열 복사, `tickOwner` 기본 인자, `tickEffectSlots` 의 매 프레임 `filter`, 설치물 팀 Map 순회. 투사체 루프 필드를 생성자에서 미리 선언.

과부하에서만 결과가 바뀌는 변경 (예산, 위 표): `CARD_EVENT_BUDGET` 600, `ENEMY_UPDATE_BUDGET` 3000 → 800 (과밀 렌더·겹침 해소 기준은 `CROWD_ENEMIES` 3000 으로 분리), `SHOT_UPDATE_BUDGET`, `ZONE_UPDATE_BUDGET`. 일반 플레이(`play-stages` 3시드)는 예산을 켠 상태로도 결과가 동일하다. RICH_DECK `stage6`·`stage7` 2400 프레임에서 카드 이벤트가 상한에 닿은 프레임은 1~2 개였다 (프레임당 최대 1100~1200).

해 보고 버린 것: 쿨타임 표의 수면 연장(쿨타임 누적 순서가 달라져 `decoy` 지문 변경), 버려지는 표본의 지수 백오프·생성 프레임 표본 생략(갱신이 오히려 늘었다), 잠든 단순 탄의 펼친 경로(A/B 에서 이득 없음), 카드 이벤트 상한 400 (이득 없음).

남은 비용과 다음 단계: 투사체 잠든 갱신(프레임당 ~1000 번 `napCheck`+`napRun`)과 새 탄의 첫 갱신, 적의 쿨타임 슬롯 갱신(프레임당 ~120 번 전체 갱신), 장판 이벤트 처리(대상당 ~10µs), GC (프레임당 약 3.5MB 할당). 더 줄이려면 투사체를 적처럼 SoA 로 옮겨 잠든 탄 이동을 C 로 하는 것이 다음 큰 단계다. 실제 게임에서는 `MAX_FX`·`MAX_TEXTS`·`MAX_PARTICLES` 가 아직 `Infinity` 라(벤치는 이펙트를 끔) 카드 이벤트마다 생기는 글자·이펙트 상한도 필요하다.

벤치 도구 추가: `tenk` 시나리오, `BENCH_PHASES`(단계별), `BENCH_PHASE_SPIKE=ms`(느린 프레임의 단계), `BENCH_COUNT=이름,…`(호출 수·호출당 µs, `fn.함수`·`클래스.메서드`, `BENCH_COUNT_KIND=1` 이면 개체 종류별), `BENCH_INFO`(장판·적 슬롯 구성), `BENCH_CAL`(기준 작업 대비 비율), `BENCH_CPU`(프로세스 CPU 시간), `BENCH_HIGH`(프로세스 우선순위), 카드 이벤트/프레임 통계.

## 10000 개체 7차: 과밀 렌더 — 글자·이펙트·파티클 상한, 탄 솎아 그리기

| render (`g.render()` 주 스레드 시간) | 변경 전 | 변경 후 |
| --- | --- | --- |
| 평균 | 45 ~ 90ms | 9.2 ~ 10.9ms |
| p95 | 59 ~ 141ms | **12.3 ~ 14.5ms** |
| 쌓인 글자 / 이펙트 / 파티클 | 16517 / 275 / 789 | 150 / 120 / ≤ 800 |

바뀐 것:
- **과밀 이펙트 상한** (`js/sim/tuning.js` 의 `CROWD_MAX_TEXTS` 150 · `CROWD_MAX_FX` 120 · `CROWD_MAX_PARTICLES` 800, `js/sim/fx.js`): 적이 `ENEMY_UPDATE_BUDGET` 또는 탄이 `SHOT_UPDATE_BUDGET` 보다 많을 때만, 다 차면 새로 생기는 글자·이펙트·파티클을 버린다 (가장 오래된 것을 지우는 `splice` 대신이라 생성 비용도 줄고, 파티클 난수는 그대로 소비한다). 값은 워커 스냅샷 상한(글자 150·이펙트 120·파티클 800)과 같다. 평소 장면은 그대로. 글자 그리기만 약 70ms 였다.

GPU 포함 시간 (후속 측정): 앞서 적은 「`getImageData(0,0,1,1)` 을 넣으면 ~58ms」는 GPU 처리량이 아니라 **readback 한 번의 왕복 지연**이었다. 이 VM 의 GPU 는 SwiftShader 가 아니라 Intel Iris Xe (ANGLE D3D11) 다.
- 빈 2D 캔버스에 256px 캔버스를 한 번 `drawImage` 하고 `getImageData` 하기를 반복하면 매번 26~106ms 가 걸린다. readback 없이 같은 그리기 200 번은 rAF 한 프레임 안에 끝난다. 그리기 내용과 거의 무관한 고정 지연이라, 거의 빈 장면도 readback 을 넣으면 35~44ms 가 나왔다.
- 그래서 GPU 포함 시간은 readback 없이 `main.js` 의 실제 rAF 루프를 vsync·프레임 상한 없이 (`--disable-gpu-vsync --disable-frame-rate-limit`) 돌려 프레임 간격으로 쟀다. 정상 상태(적 5550 · 탄 5000, 화면 안 탄 ~1970)까지 돌린 뒤 시뮬레이션을 멈추고 그리기만 반복했다. 빈 장면의 프레임 간격은 3.5ms 다.

- **함께 고친 오류**: `enemy.js` 의 `drawOverlays` 가 분리되며 `sy` 를 잃어, 방패를 든 적(`bastionWarden`·`darkKnight`, `entityGuard`)이 화면에 있으면 `render()` 가 `sy is not defined` 로 멈췄다. `draw` 와 같은 식(빙결이 아니면 흔들림 포함)으로 그 자리에서 계산한다. 모든 적 종류를 하나씩 그려 오류가 없음을 확인했다.
- 남은 것: `slot.has` (render CPU 의 8.6%, `drawOverlays` 가 그려지는 적마다 `entityGuard`·`armor` 를 묻는다). 슬롯 판정은 시뮬레이션과 함께 쓰는 코드라, 렌더만 바꿔서는 줄일 수 없다. 카드 목록이 바뀔 때만 다시 계산하는 표시용 캐시를 슬롯 쪽에 두는 것이 다음 단계다.
- 한계: 측정 중 다른 학습 작업이 CPU 를 100% 쓰는 때가 많아 같은 조건의 p95 가 15ms 에서 190ms 까지 흔들렸다. 위 표는 경합이 덜했던 구간의 값이다. 경합이 없을 때 GPU 포함 p95 는 16ms 경계 근처다.
