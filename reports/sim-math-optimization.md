**부동소수점 이동 최적화를 기본으로 사용한다.** 전체 게임의 속도 이득은 아래 측정에서 확인하지 못했지만, 플레이 후 사용자의 선택에 따라 기본 모드로 적용했다. `SIM_MATH=exact` 또는 브라우저 `?math=exact` 로 원래 계산을 선택할 수 있다 (워커에도 같은 모드).

2026-11-02, Windows x64, Node v22.14.0, Intel Core i5-1135G7. 분석 대상은 JS/WASM 시뮬레이션이며 렌더 시간은 제외했다.

적용한 실험은 다음과 같다. 좌표·속도·수학 함수의 자료형은 기존 부동소수점 그대로다.

- 방향 벡터 → `atan2` → `sin/cos` 왕복을 벡터 정규화로 대체.
- WASM 적 이동에서 같은 거리의 중복 계산을 재사용하고, 거리 유지가 없을 때 불필요한 거리 계산을 생략.
- 보통 범위의 2차원 `hypot` 를 `sqrt(x*x+y*y)` 로 계산. 오버플로·언더플로·NaN·무한대는 기존 함수로 처리.
- 이동 각도의 `atan2` 를 다항식으로 근사하고, 유도탄의 각도 차는 삼각함수 3회 대신 나머지 연산으로 계산.
- 피해량·쿨타임·충돌 거리 판정식·개체의 스탯/슬롯/카드 스택 구조는 유지.

원래 경로는 `SIM_MATH=exact` 로 선택한다. 변경 전 HEAD `473c7b3` 에서 먼저 측정한 600프레임 상태 지문 4개(`enemies`, `crowd`, `hold`, `tenk`)를 정밀 모드에서 모두 재현했다. 아래 A/B는 같은 빌드 안의 원래 계산 경로와 실험 경로를 비교한다.

같은 입력 4,096개로 실제 WASM `nap_move` 를 호출하고, 매 회 입력을 복구했다. 순서를 교대해 모드별 40회 준비 후 120회 측정한 중앙값이다. 입력 복구는 측정에서 제외했다.

| 이동 커널 | 원래 계산 | 실험 | 시간 감소 |
| --- | ---: | ---: | ---: |
| 기존 각도 방향 이동 | 0.351ms | 0.228ms | 34.8% |
| 대상 추적 | 0.251ms | 0.146ms | 42.0% |
| 대상과 거리 유지 | 0.257ms | 0.158ms | 38.5% |

별도 함수별 재측정에서도 이동 커널은 31.5~40.7% 단축됐다. JS 함수만 같은 입력으로 비교하면 거리 계산 28.8%, 각도 계산 27.7%, 각도 차 계산 53.7% 단축됐지만, 이 값 역시 전체 프레임의 향상률은 아니다.

전체 게임은 고정 시드 7, 시나리오별 1,200프레임 중 앞 400프레임 제외, 모드별 5회 실행의 평균 프레임 시간 중앙값이다. 실행 순서를 exact→fast / fast→exact 로 교대했다. 1차 5회 비교 뒤 변동이 커서, 아래 2차 측정에는 프로세스 우선순위 상향 옵션과 매 프레임 기준 작업(`BENCH_CAL=1`)을 사용했다. 일반 시나리오는 1/60초 틱, stage7은 기존 도구 설정인 1/20초 틱이다.

| 시나리오 | 원래 계산 평균 / p95 | 실험 평균 / p95 | 평균 시간 감소 | 기준 작업 대비 보정 |
| --- | ---: | ---: | ---: | ---: |
| enemies | 0.164 / 0.309ms | 0.167 / 0.310ms | −1.8% | +2.3% |
| crowd | 0.885 / 2.025ms | 0.857 / 1.968ms | +3.2% | +4.4% |
| hold | 4.466 / 7.419ms | 4.685 / 7.632ms | −4.9% | −1.0% |
| tenk | 5.962 / 13.501ms | 6.345 / 14.323ms | −6.4% | +4.2% |
| stage7 | 5.323 / 7.857ms | 7.024 / 11.086ms | −32.0% | −3.5% |

양수는 시간 감소, 음수는 증가다. p95 역시 실행별 p95의 중앙값이며, 모든 프레임을 합친 p95는 아니다. 보정값은 모드별 `평균 step 시간 / 평균 기준 작업 시간`의 중앙값 비율로, 참고 지표다. 기준 작업은 렌더가 아니며 측정 구간 밖에서 실행한다.

전체 게임의 결과를 순수한 산술 속도 향상률로 해석할 수는 없다. 같은 모드에서도 실행별 편차가 컸고, 근사 이동으로 충돌·난수 소비·이후 개체 수가 달라졌다. 1차와 2차의 증감 방향도 대부분 일치하지 않았다. 특히 stage7의 원시 시간 32% 증가는 기준 작업으로 보정하면 3.5%가 되어, 환경 변동과 게임 작업량의 영향을 분리하기 어렵다. 보정 후에도 전 시나리오에서 일관된 이득은 없다.

| 종료 상태 (원래 → 실험) | 적 | 탄 | 처치 |
| --- | ---: | ---: | ---: |
| enemies | 131 → 131 | 0 → 0 | 39 → 39 |
| crowd | 18 → 18 | 6 → 6 | 540 → 540 |
| hold | 2,783 → 2,777 | 1,313 → 1,302 | 0 → 0 |
| tenk | 8,743 → 8,446 | 5,646 → 5,604 | 0 → 0 |

`hold`·`tenk` 는 목표 수보다 적어졌을 때 채우므로 실제 개체 수가 목표를 초과한다. 작은 오차도 장기 전투의 이벤트 순서를 갈라놓을 수 있어, 최종 상태 지문의 일치는 근사 모드의 합격 조건으로 삼지 않았다.

오차 검사에서는 사분면 전 구간 800,004표본과 다양한 크기의 난수 100,000표본을 확인했다. 특수값·JS/WASM 수치 일치·기존 정밀 경로도 검사했다.

| 항목 | 관측 최대 |
| --- | ---: |
| atan2 각도 오차 | 0.00001149143rad ≈ 0.0006584도 |
| 거리 상대 오차 | 4.44×10⁻¹⁶ |
| 60초 대상 추적·공포·거리 유지 실험의 위치 차이 | 1.02×10⁻¹²px |
| 60초 유도탄 추적 실험의 위치 차이 | 0.10647px |

60초 위치 차이는 해당 고정 경로의 관측값이며 모든 전투의 오차 상한이 아니다. 정상 범위에서 벗어난 입력은 정밀 함수로 되돌린다. 기존 정밀 수학 200만 표본의 비트 일치 검사와 `npm run check` 는 통과했다.

규칙 검사 36개를 정밀·근사 모드로 각각 실행했고, 각 모드에서 26개 통과·3개 생략·7개 실패로 동일했다. 기존 VM 검사에도 `process.env.SIM_MATH` 를 전달해 근사 경로가 실제로 선택되도록 했다. 브라우저 검사 3개는 `playwright` 부재로 생략했다. 실패 7개는 HEAD `473c7b3` 를 별도 임시 폴더에 추출해 동일한 오류를 재현했으며, 이번 변경과 무관하다.

- `check-basic-state-inheritance`, `check-entity-slots`, `check-event-slots`, `check-explicit-actions`, `check-teams`: `queryStructs` 의 출력 배열이 없어 `out.length` 에서 실패.
- `check-gimmick-bosses`: 검사에서 `rollRewards` 를 로드하지 않아 실패.
- `check-targets`: 검사에서 `UI.updateRewards` 가 없어 실패.

새 수치 오차 검사와 장시간 객체 재사용 검사는 두 모드 모두 통과했다. 전체 검사 묶음이 모두 통과했다고 판단한 것은 아니다.

판단: 이동 연산 자체는 확실히 줄었지만, 슬롯·이벤트·대상 검색 등 나머지 비용이 남아 전체 시뮬레이션 개선으로 이어진다는 근거는 부족하다. 이 측정 결과는 유지하며, 기본 플레이는 근사 최적화, 정밀 경로는 비교 옵션으로 제공한다.
