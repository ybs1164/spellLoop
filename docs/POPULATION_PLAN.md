# 개체 수 폭증 방지 기획

목표: 카드 기믹이 만드는 **폭발적인 증식 장면은 살리고**, 시뮬레이션이 감당하지 못하는 무한 증식만 막는다. 규칙은 「모든 개체는 스탯·슬롯·카드 스택으로 정의된다」는 원칙 안에서, 가능한 한 **카드 쿨타임 연산**으로 표현한다.

> 폐기한 안
> - 수명 보존 법칙(분열·생성 때 수명을 나눔): 분열할수록 개체가 짧아져 폭발적인 장면이 나오지 않는다.
> - 군체(같은 개체를 합쳐 `수량` 스탯으로 표현): 구현·판정 비용 대비 효과가 불확실하다.

## 0. 결정 사항

| 항목 | 선택 | 근거 (§3 측정) |
| --- | --- | --- |
| 생성 카드 쿨타임 | 소환·포탑·부유 구체의 `×` 할인을 `+` 연산으로 바꾼다 (측정값: 소환 `+1`, 포탑 `+1`, 구체 `+0.5`) | 체인 덱의 폭주는 재귀가 아니라 `×` 할인이 곱으로 쌓여 매 프레임 작동한 것이다. 바꾸면 5000 초과 → 311 |
| 분열 쿨타임 | `+1` → `+2`~`+3` | +2 에서 아군·분신 분열이 20~30 선, +5 이상은 폭발감이 사라진다 |
| 복제 대상 면역 (미측정) | 한 개체는 일정 시간 한 번만 분열 대상이 되고, 방금 생긴 복제는 그 프레임에 분열 대상이 되지 않는다 | `전체 → 분열` 은 쿨타임과 무관한 **한 프레임 안의 연쇄**라 타이머로 막을 수 없다 |
| 설치물 분열 | 별도 제약 필요 (설치물 수명 단축 또는 설치물 분열 전용 페널티) | +3 에서도 약 6초마다 2배 |
| `전체 → 생성` | 별도 제약 필요 | `+1` 포탑으로는 30초 동안 2207 까지 계속 증가 |

## 1. 문제: 증식 고리

| 고리 | 예시 | 측정 전 가설 | 측정 후 실제 |
| --- | --- | --- | --- |
| A. 분열 복제 | 분신·아군·설치물·장판이 `분열` 슬롯을 계승(`inheritEntitySlots`) | 쿨타임마다 2배 | 아군·분신·장판은 남은 수명을 물려받아 계보가 끝나므로 묶인다. **설치물만** 수명이 길어 계속 2배 |
| B. 생성 연계 | `포탑 → 포탑 → 포탑`, `소환 → 소환 → 소환` | 시간에 따른 기하급수 | 행동 스택은 단계마다 꼬리가 줄어(`slot-events.js` `executeLinkedAction`) **카드 수만큼만** 이어진다. 폭주 원인은 `×0.25` 3장 = 0.016초, 즉 매 프레임 작동 |
| C. 자기 참조 대상 | `전체 → 분열`, `전체 → 포탑` | 실행마다 N → 2N | `전체 → 분열` 은 **한 프레임 안에서** 2^k 배 (§3.4). `전체 → 포탑` 은 선형이지만 기울기가 크다 |
| D. 분신 증폭 | 분신이 플레이어 덱 전체를 계승 | — | 기하급수는 아니지만 분신 수 × 다른 생성 슬롯으로 곱해진다 (§3.1) |

## 2. 방법론

- **Adams & Dormans, 『Game Mechanics: Advanced Game Design』**: 증식은 배수구 없는 양의 되먹임 엔진이다. 측정으로 **실제 엔진**(설치물 분열, 한 프레임 연쇄)과 겉보기 엔진(체인, 분신)을 구분하고, 진짜 엔진에만 제동을 건다.
- **Schreiber & Romero, 『Game Balance』**: 비용 곡선에서 곱 할인은 쌓을수록 비용이 0 으로 수렴하는 구멍이다. 생성 카드는 합연산으로 비용을 매겨 쌓을수록 비싸지게 한다.
- **Jesse Schell, 『The Art of Game Design』 — 본질적 경험의 렌즈**: 지켜야 할 경험은 「빌드가 폭주한다」는 감각이다. 페널티는 이 감각이 남는 한계(분열 +2~+3)에서 멈춘다.
- **Salen & Zimmerman, 『Rules of Play』**: 같은 프레임에 발동이 몰리는 동기화는 되먹임이 지연 없이 즉시 닫히는 고리다. 대상 면역은 고리에 지연을 넣는 부정 되먹임이다.

## 3. 측정

### 3.0 조건

- headless 30초, `dt = 1/60`, 고정 시드. 적 60마리(무적·정지), 자연 스폰 끔.
- 플레이어 시작 덱에서 이동 슬롯만 남기고 측정 덱을 넣는다 (§3.1 이전 측정은 시작 덱의 마탄·부유 구체 슬롯이 섞여 있었다).
- 수치는 아군 + 설치물 + 장판의 최대값(스테이지 화약통 3~4개 포함). 5000 초과 또는 한 프레임 1.5초 초과 시 중단.
- 스크립트: `measure-pop.cjs` (세션 scratchpad, 저장소 밖). 정식 도구는 `tools/check-population.cjs` 로 옮길 예정 (§4).

| 덱 | 슬롯 |
| --- | --- |
| 플레이어 분열 | `플레이어 → 분열` |
| 아군 분열 | `무작위 지점 → 기사 소환`, `아군 → 분열` |
| 전체 분열 | `무작위 지점 → 기사 소환`, `전체 → 분열` |
| 설치물 분열 | `전방 지점 → 부유 구체`, `설치물 → 분열` |
| 장판 분열 | `전방 지점 → 독 장판`, `장판 → 분열` |
| 포탑 체인 | `가장 가까운 적 → 포탑 → 포탑 → 포탑` |
| 소환 체인 | `가장 가까운 적 → 기사 소환 → 기사 소환 → 기사 소환` |
| 전체 포탑 | `전체 → 포탑` |

### 3.1 분신 의심 동작

시작 덱을 둔 채 `플레이어 → 분열` 을 돌리면 설치물이 964개까지 늘었다. 추적 결과 버그가 아니다: 분신이 시작 덱의 `전방 지점 → 부유 구체` 슬롯을 계승해 분신마다 구체를 설치했다 (구체 1,200개 중 1,136개가 분신 설치). 분열 경로는 정상이었다(플레이어 → 분신, 분신 → 아군 경로).

### 3.2 같은 페널티를 분열·소환·포탑에 일괄 적용

| 덱 | 기본 | +5 | +10 |
| --- | --- | --- | --- |
| 플레이어 분열 | 34 | 6 | 4 |
| 아군 분열 | 443 | 10 | 7 |
| 전체 분열 | 150초 안에 못 끝냄 | 150초 안에 못 끝냄 | 20 |
| 설치물 분열 | **5000 초과 @22초** | 125 | 76 |
| 장판 분열 | 12 | 7 | 7 |
| 포탑 체인 | 2193 (선형 증가) | 307 | 307 |
| 소환 체인 | **5000 초과 @11.9초** | 104 | 104 |
| 전체 포탑 | **프레임 1.8초 @14초** | 667 | 322 |

- 체인 덱은 +5 와 +10 의 최대값이 같다: 연계 슬롯은 쿨타임을 보지 않아(`slot-runtime.js` `runEventSlot` 의 `cooled`) 페널티는 첫 슬롯만 늦춘다.
- +5 이상은 분신·아군 분열을 한 자리 수로 만들어 폭발감이 사라진다.

### 3.3 분열 +1~+3, 생성 카드 합연산 (소환 `+1`, 포탑 `+1`, 구체 `+0.5`)

| 덱 | 분열 +1 | 분열 +2 | 분열 +3 |
| --- | --- | --- | --- |
| 플레이어 분열 | 34 | 19 | 10 |
| 아군 분열 | 54 | 32 | 26 |
| 전체 분열 | **메모리 부족** | **메모리 부족** | **메모리 부족** |
| 설치물 분열 | **5000 초과 @22초** | 1404 (증가 중) | 401 (증가 중) |
| 장판 분열 | 12 | 8 | 9 |
| 포탑 체인 | 481 | 481 | 481 |
| 소환 체인 | 311 | 311 | 311 |
| 전체 포탑 | 2207 (증가 중) | 2207 | 2207 |

- 합연산 전환으로 체인 덱은 묶인다. `전체 포탑` 에는 `+1` 이 이전 `×0.8` 보다 약해 오히려 늘었다.
- 설치물 분열은 복제가 수명을 물려받지만 구체 수명이 길어 30초 안에 계보가 끝나지 않는다.

### 3.4 `전체 → 분열` 의 한 프레임 폭주

- 쿨타임이 끝난 **한 프레임**(6.48초)에 분열이 4만 번 넘게 실행되며 아군 2만, 설치물 1.6만까지 늘다 메모리가 바닥났다.
- 원인: 복제가 원본의 남은 쿨타임을 복사해(`entity-gimmicks.js` `inheritEntitySlots` 의 `copy.cd = slot.cd`) 같은 프레임에 함께 발동하고, 그 프레임에 생긴 복제도 곧바로 갱신되어 다시 `전체 → 분열` 을 실행한다.

### 3.5 복제 쿨타임 초기화 패치 (측정 스크립트에서만, 분열 +2)

복제의 일반 슬롯 쿨타임을 `slotCooldown + 1프레임` 으로 새로 시작하게 했다.

| 덱 | 결과 | 패치 전 |
| --- | --- | --- |
| 전체 분열 | **메모리 부족 @16.5초** | 메모리 부족 @6.5초 |
| 나머지 7종 | 패치 전과 거의 같다 | — |

- 폭발 시점만 늦춰졌다. 한 번의 `전체 → 분열` 로 같은 프레임에 태어난 형제 분신들이 **같은 새 쿨타임**을 받아 다시 함께 발동하고, 발동마다 `전체` 를 다시 골라 앞선 형제의 복제까지 나눈다 → 한 프레임에 2^k 배 (분열 2.4만 번 중 2.2만 번이 분신 실행).
- **결론: 행동하는 쪽 쿨타임으로는 막을 수 없고, 나뉘는 쪽에 제한이 필요하다.**

## 4. 규칙 명세 (안)

1. **생성 카드 합연산**: `summon`, `turret`, `orb` 의 쿨타임 연산을 `×` 에서 `+` 로 바꾼다. `archer`(`×0.4`), `boomerang`(`×0.45`) 등 다른 `×` 할인 카드도 같은 기준으로 검토한다.
2. **분열 `+2`**: 분열 카드 쿨타임 연산을 `+1` → `+2` 로 올린다 (+3 은 분신 분열이 10 선이라 감각을 보고 결정).
3. **분열 대상 면역**: 분열된 원본과 복제는 일정 시간(안: 분열 기본 쿨타임) 동안 다시 분열 대상이 되지 않는다. 같은 프레임에 k 개가 발동해도 증가가 많아야 2배로 묶이고, 발동 연출은 그대로 남는다. 개체 스탯(면역 시간)으로 표현한다.
4. **설치물 분열**: 설치물 수명 단축, 또는 설치물 대상 분열에만 추가 페널티. 측정으로 고른다.
5. **`전체 → 생성`**: 대상 수에 비례하는 쿨타임(`전체` 의 `×3.5` 이후에 생성 카드 `+` 가 더해지는 순서 문제 포함)을 검토한다. 배치 순서에 따라 `+` 페널티가 뒤의 `×` 카드에 깎이지 않도록, 페널티를 슬롯 쿨타임의 하한으로 거는 안도 있다.
6. **안전망**: `tuning.js` 의 `SPLIT_CAPS`·`MAX_*_PER_KIND` 는 지금 스트레스 테스트로 `Infinity` 다. 위 규칙 적용 후 측정 최대값보다 위로 되돌려, 정상 플레이에서 닿지 않는 안전망으로만 쓴다.

## 6. 열린 질문

- 분열 +2 와 +3 중 어느 쪽이 원하는 폭발감인가 (분신 분열 최대 19 vs 10).
- 생성 카드 `+` 값(소환·포탑 `+1`, 구체 `+0.5`)은 측정용 임의값이다. 단일 카드 슬롯의 체감 속도와 맞춰 정해야 한다.
- 분열 대상 면역 시간: 분열 기본 쿨타임과 같게 둘지, 별도 스탯으로 둘지.
- 분신이 플레이어 덱 전체를 계승하는 것(§3.1)을 의도대로 유지할지.
